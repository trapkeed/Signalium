---
name: S28 Compliance and Audit Infrastructure
description: Hash-chain tamper resistance, account deletion PII scrubbing, signed exports/tokens, and dedup pitfalls for compliance features.
---

- Tamper-evident audit log: added a hash chain (eventUuid/sequenceNum/prevHash/hash) directly onto the existing `audit_log` table rather than a parallel table. Writes are serialized with a transaction-scoped Postgres advisory lock (`pg_advisory_xact_lock`) inside `logAudit` so concurrent appends can't race on `sequenceNum`.
  **Why:** a single shared append-only log with one lock key is simpler to verify than sharding locks per actor, and reusing the existing table avoids a second logging system.
- `verifyAuditChain()` must trust the oldest *surviving* row's `prevHash` as its starting point, not require it to be null — the audit-retention sweep (existing, 730-day default) prunes old rows, which permanently removes the earliest chain links. Treating that as "broken" is a false positive, not tampering.
  **How to apply:** any tamper-evident chain that coexists with a retention/pruning job needs this "trust the prefix boundary" adjustment, or verification will always report a break after the first sweep.
- Account deletion is soft-delete (anonymize + deactivate), never hard-delete, because payments/subscriptions/audit history must survive for compliance retention. Anonymization must be swept across **every** user-linked table with direct identifiers, not just the `users` row — missed fields (login IP/city/country/device/browser/session-id, consent IP/user-agent) were flagged twice in review before being fully scrubbed.
  **Why:** "the users row is anonymized" is not equivalent to "the user's PII is gone" when other tables key on the same userId and store their own identifying strings.
  **How to apply:** when adding anonymization, grep every table with a `userId` column for text fields that could identify a person (IP, device, email, name, free-text), not just the obviously-named ones.
- A column with a unique index (e.g. `login_events.clerkSessionId`) can't be overwritten with one constant value across multiple rows in a single `UPDATE ... SET x = 'literal'` — use a SQL fragment evaluated per row (e.g. `sql\`'deleted-' || gen_random_uuid()\``) so each row gets a distinct value.
- Preventing duplicate "active" workflow state (e.g. only one non-terminal account-deletion request per user) needs both a DB-level partial unique index (`where status in (...)`) as the real backstop AND an app-level pre-check for a friendly error — the pre-check alone has a race window, so also catch the DB unique-violation (Postgres code `23505`) and map it to the same user-facing response.
- Audit-log dedup on toggle-style actions (emergency stop, autonomous mode): only log when the value *actually changes* relative to the existing row, and explicitly handle the "no row exists yet" case (don't treat `existing === undefined` as "already at the target state" if that produces a spurious log on first call, or as "changed" if it doesn't).
- Signing: HMAC-SHA256 keyed by the existing `SESSION_SECRET` (already a rotated/managed secret) is reused for two distinct purposes — self-describing expiring confirmation tokens (email-delivered, e.g. account-deletion confirm) and integrity signatures over on-demand export payloads. Don't duplicate this with a new secret unless the trust boundary actually differs.
- Data export is synchronous/on-demand JSON with only a payload-hash record persisted — deliberately avoids holding a second copy of personal data at rest.
