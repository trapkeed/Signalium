---
name: S24C SSO Identity Provider
description: Additive admin-role model, asymmetric JWT/JWKS signing, and refresh-token rotation pitfalls from building Signalium's SSO/RBAC layer.
---

- **Additive role table over enum rewrite**: fine-grained named roles (SuperAdmin/Admin/Founder/QuantResearcher/MLResearcher/DeploymentApprover/Auditor) were added as a separate many-to-many table, not by rewriting the existing coarse `users.role` enum. Effective roles are computed at read time (legacy role implication + explicit grants + active assumption) rather than backfilled — avoids a migration and keeps legacy `requireAdmin`/`requireStaff` routes unchanged. **Why:** backward compatibility was a hard requirement; a live enum rewrite risks breaking every existing admin route. **How to apply:** reuse this pattern (implication function, not backfill rows) whenever layering fine-grained roles on top of an existing coarse tier.

- **Asymmetric signing key persisted in DB, not env secret**: the SSO JWT signing key (ES256 keypair) is generated once on first boot and stored in a `sso_signing_keys` table (private key as JWK), not requested from the user as a secret. **Why:** avoids an interactive secret-provisioning step for something the service can safely self-generate and rotate; `requestSecrets` is for user-supplied/external credentials, not internal signing material the app fully owns. **How to apply:** for any future service-owned signing/encryption key, default to DB-persisted generate-on-first-use rather than asking the user for a secret.

- **Refresh-token rotation must be one atomic conditional UPDATE, not read-then-write**: a `SELECT ... WHERE revokedAt IS NULL` followed by a separate revoke UPDATE lets two concurrent refresh calls both pass the read and each mint a valid successor token, breaking single-use rotation. Fix: `UPDATE ... SET revokedAt = now() WHERE revokedAt IS NULL AND expiresAt > now() RETURNING *` — only the request that actually flips the row wins. **Why:** caught in code review on this build; the read-then-write version compiled and worked in the happy path but was a replay hole under concurrency. **How to apply:** any single-use-token consumption (refresh tokens, single-use invite codes, etc.) should claim via a conditional UPDATE...RETURNING, never a separate read then write.

- **JWT audience must be mandatory at verification time, not optional**: `verifyAccessToken`/a `/verify` convenience endpoint that accepts a missing `aud` and still validates allows a token minted for one downstream service to be replayed against another (token confusion). Require callers to pass the expected audience and reject if absent. **Why:** caught in code review; jose's `jwtVerify` only checks audience if you pass one in options. **How to apply:** never make `audience` optional in a token-verification helper meant for service-to-service auth.

- **Service/machine tokens should carry least-privilege scope claims, not a reused human admin role**: initial version minted the platform's own outbound-to-Trainer service token with `roles: ["super_admin"]` for convenience; corrected to an empty `roles` array plus a narrow `scope: ["trainer.inference"]` claim so a leaked service token grants nothing admin-equivalent. **Why:** caught in code review; reusing an admin role for a machine identity maximizes blast radius on leak for no functional benefit. **How to apply:** give machine/service JWTs their own `scope` claim vocabulary, separate from human `roles`, sized to exactly what the caller needs.
